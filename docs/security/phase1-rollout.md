# Database hardening rollout — prepared, not applied

The code release does not establish that the live database is secure or reachable. `phase1-hardening.sql` is deliberately outside automatic migrations. It changes permissions and must be checked against the actual service and an administrator identity before execution. No new plugin is needed: an authorized owner's service dashboard or existing database connection is sufficient.

1. Export the current policy definitions, grants, bucket public flags, and schema. Verify which project and environment the connection targets. Keep a backup and identify the previous policy state for recovery.
2. Through trusted Auth administration, assign `app_metadata.role = admin` to the confirmed owner account. Do not trust editable `user_metadata`. Verify this is a permanent account and retain an owner-level database connection during rollout. The script aborts if no such administrator exists. Never select a user by guessing an email or UUID.
3. Inventory public, draft and internal media. Verify every published image has a working delivery route. Current stable local assets remain valid; private live storage delivery requires server signing to work. Make the `project-media` bucket private only after published delivery has been tested. The SQL aborts if the bucket is still public; it never flips this flag silently.
4. Before applying the lead constraint, inspect existing rows that fail its email/message bounds and reconcile them: NOT VALID still checks subsequent updates. Apply the SQL on an isolated staging copy first. It adds restrictive guards alongside historical permissive policies, validates actual trusted admin state, scopes anonymous media to publication-approved objects, checks audit identity and constrains new lead sizes. Review any additional live roles/policies: the script covers `anon` and `authenticated`, not undiscovered custom roles or a leaked service key.
5. Test the real API as: unsigned public visitor; signed-in anonymous user; ordinary account; authorized administrator. Ordinary accounts must not read enquiries, publish/edit records, upload/delete project media, or forge audit entries. Published public pages and approved media must remain accessible. Use a known internal object to verify direct unauthenticated download denial, not only storage listing.
6. Exercise publication/unpublication and media-flag changes. A previously public object must stop being anonymously readable after withdrawal; consider CDN and already-issued signed URL lifetime. Verify anonymous enquiry insertion permits valid bounded records but not oversized/empty submissions.
7. Apply to production only after these checks pass. Verify admin operations, public pages, media, and lead receipt immediately. Record deployed policy names and evidence. The site is using archive recovery while its upstream is unavailable; this script does not resume or restore that source.

Local verification uses real PostgreSQL via PGlite with representative Auth/storage/table fixtures. It proves SQL syntax and tested RLS behavior, including a legacy broad-policy baseline, but does not emulate Supabase Storage's HTTP server or prove production settings.

Remaining service-level work: durable distributed abuse controls (for example a WAF limit or verified challenge), notification/outbox delivery and operational alerts need the actual service configuration. The application does not claim to provide a distributed rate limiter or an outage-independent queue. Its honeypot is an auxiliary filter, not authorization or comprehensive spam prevention. No automatic POST retries are introduced: a timeout may follow a successful commit, so operators should check receipt before resubmitting a potentially duplicated enquiry.

References: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Storage access control](https://supabase.com/docs/guides/storage/security/access-control).
